# Deploying Fakturly

Three pieces, three hosts, all on free tiers:

| Piece | Host | Why this one |
|---|---|---|
| API + Redis | **Render** (Docker, Frankfurt) | Runs the `Dockerfile` as is, has managed Redis, health-checks before routing traffic |
| PostgreSQL | **Neon** (or Supabase) | Render's free database expires after 90 days; Neon's does not |
| Frontend | **Vercel** | Static files with a CDN; one rewrite rule for the SPA |

The demo deployment runs with `DEMO_MODE=true`, which publishes the demo
logins at `GET /demo` and rebuilds the dataset every night at 03:00. A real
deployment leaves it off — the route then does not exist at all.

---

## 1. Database — Neon

1. neon.tech → New project → region **Frankfurt** (closest to Render's).
2. Copy the connection string. It looks like
   `postgresql://user:pass@ep-...eu-central-1.aws.neon.tech/neondb?sslmode=require`.

That is `DATABASE_URL`. Nothing else to do: the API applies its own
migrations on every start (`docker-entrypoint.sh`).

> Supabase works the same way. Use the **session pooler** connection string
> (port 5432), not the transaction pooler — Prisma migrations need session
> semantics.

## 2. API — Render

1. render.com → **New → Blueprint** → connect the GitHub repo.
   Render reads `render.yaml` at the root and proposes two services:
   `fakturly-api` and `fakturly-redis`.
2. Fill in the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | from step 1 |
   | `FRONTEND_URL` | your Vercel URL, e.g. `https://fakturly.vercel.app` — **no trailing slash**, it is compared to the browser's `Origin` header for CORS |
   | `STRIPE_SECRET_KEY` | `sk_test_...` — see [integrations.md](integrations.md) |
   | `STRIPE_WEBHOOK_SECRET` | from the Stripe dashboard webhook you create in step 4 |
   | `RESEND_API_KEY` | `re_...` |

   `JWT_SECRET` is generated by Render (`generateValue: true`) and
   `REDIS_URL` is wired from the Redis service. `NODE_ENV=production` means
   `env.ts` refuses to boot if any of the Stripe or Resend keys are missing —
   deliberately, so a demo cannot go live with payments silently disabled.

3. Deploy. The first start runs `prisma migrate deploy` against the empty
   Neon database, then listens. Watch the logs for
   `[scheduler] DEMO MODE — nightly reset scheduled`.

4. Seed the demo data once. Render → the service → **Shell**:

   ```bash
   bun run seed:demo
   ```

   From then on the nightly job keeps it fresh.

5. Check: `https://<api>.onrender.com/health/ready` should answer
   `{"status":"ready","database":"up","redis":"up"}`.

> **Free tier caveat:** Render spins a free web service down after 15 minutes
> without traffic, and the next request takes 30–60 seconds while it wakes.
> The landing page will feel slow the first time someone opens it. If that
> matters for a demo, the Starter plan removes it.
>
> **The nightly reset needs the process alive at 03:00.** A spun-down service
> runs no cron. Either keep it awake with an external ping every 10 minutes
> (cron-job.org, UptimeRobot), or run `bun run seed:demo` from the Render
> shell before showing the demo. For a free tier the ping is the honest option.

## 3. Frontend — Vercel

1. vercel.com → **Add New → Project** → import the repo.
2. Settings:

   | Setting | Value |
   |---|---|
   | Root Directory | `frontend` |
   | Framework | Vite |
   | Build command | `bun run build` |
   | Output directory | `dist` |

3. Environment variable: `VITE_API_URL` = the Render URL from step 2, **no
   trailing slash**.

   > `VITE_*` variables are baked into the bundle at build time. Changing one
   > means redeploying — it is not read at runtime.

4. Deploy. `frontend/vercel.json` rewrites every path to `index.html`, so a
   deep link like `/invoices/abc` loads the app rather than a 404 from the CDN.

5. Go back to Render and set `FRONTEND_URL` to the Vercel URL, if you did not
   know it in step 2. The API restarts and CORS now allows the real origin.

## 4. Stripe webhook

The local setup uses `stripe listen`; production needs a real endpoint.

1. Stripe dashboard (test mode) → Developers → Webhooks → **Add endpoint**.
2. URL: `https://<api>.onrender.com/webhooks/stripe`.
3. Event: `checkout.session.completed`.
4. Copy the signing secret (`whsec_...`) into `STRIPE_WEBHOOK_SECRET` on Render.

Test it end to end: log in as the demo admin, open an unpaid invoice,
**Betallänk**, pay with `4242 4242 4242 4242`. The invoice turns `PAID`
within a few seconds and the ledger shows `PAYMENT_RECEIVED`.

## What each environment variable does

The full list, with defaults, is validated in `backend/src/lib/env.ts` — that
file is the reference. The ones that matter for a deploy:

| Variable | Required in production | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Neon/Supabase, with `sslmode=require` |
| `REDIS_URL` | yes | Render wires it |
| `JWT_SECRET` | yes, ≥ 32 chars | Render generates it |
| `FRONTEND_URL` | yes | CORS allowlist and links in emails |
| `STRIPE_SECRET_KEY` | yes | test key is fine for the demo |
| `STRIPE_WEBHOOK_SECRET` | yes | from the dashboard endpoint, not `stripe listen` |
| `RESEND_API_KEY` | yes | `onboarding@resend.dev` only delivers to the account owner |
| `DEMO_MODE` | no | `true` for the showcase, absent otherwise |
| `CROSS_SITE_COOKIES` | yes, when frontend and API are on different domains | Makes the refresh cookie `SameSite=None; Secure`. Without it every page reload logs the user out (ADR 47) |
| `COMPANY_*` | no | seller details on the PDF; defaults are the fictional demo company |

## Running the image locally

```bash
cd backend
docker build -t fakturly-api .
docker run --rm -p 3000:3000 \
  -e DATABASE_URL=postgresql://devinder:secret@host.docker.internal:5432/fakturly \
  -e REDIS_URL=redis://host.docker.internal:6379 \
  -e JWT_SECRET=$(openssl rand -base64 48) \
  -e NODE_ENV=development \
  fakturly-api
```

`host.docker.internal` is how a container reaches services on the host
machine — `localhost` inside the container is the container itself.
`NODE_ENV=development` here so the Stripe and Resend stubs are allowed.
